# Payment flow
Before validation, the parsed payment object is encoded as deterministic, recursively key-sorted canonical JSON for HMAC verification. The CLI helper and Postman collection apply the identical algorithm.

The canonical JSON content is authenticated with HMAC, then validated. Amounts must have at most two decimal places so PostgreSQL cannot silently round the accepted value. The service resolves the merchant, checks the globally unique transaction reference, selects an active device, stores the payment, publishes a localized message, and records publication state. New payments require an active merchant.

An identical duplicate returns the existing transaction and does not publish. The merchant, amount, currency and payment status must match the original request. A conflicting reference returns 409 without disclosing the original transaction. Concurrent inserts resolve through the database uniqueness constraint: only the insert winner publishes, and identical losing requests read the original row. References remain globally unique for compatibility with the existing schema. A status change under the same reference is a conflict, not an update.

Replay is explicit, authenticated, limited to successful payments on active devices, and audited in `device_events`. This parent project still has no transactional outbox or device acknowledgment protocol. A crash or publish failure after persistence can leave an announcement pending. An identical retry reports stored state but does not automatically republish. A published state means broker acknowledgment, not proven audio playback. See the PayOps child project for a separate implementation of durable dispatch and signed device receipts.
